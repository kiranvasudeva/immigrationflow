Migrate Legacy Workflow References to the New Template System
The app’s workflow management needs to shift from the old “assignments” paradigm to the new template-based system for tracking worker progress. This is a crucial architectural update:
Replace Assignment Model with Workflow Progress: Identify all places in code (both front-end and backend API) where “assignments” are used. For instance, the backend has routes like PATCH /assignments/:id/status to update an assignment’s status, and the front-end likely calls these when a user uploads a document or an admin marks something complete. We need to refactor this logic to use the new worker_workflow_progress and worker_step_progress tables instead. The new model implies: a worker is assigned to a workflow template (e.g., “Work Permit Application”) via an entry in worker_workflow_progress (with an overall status and current step), and then each step of that template has a corresponding worker_step_progress entry for that worker. Therefore:
The overall workflow status (e.g., In Progress, Completed) for a worker is in worker_workflow_progress.status. We should use this instead of an assignment’s status if we were tracking an entire process as one “assignment.”
Each document/form task that was an “assignment” should now correspond to a specific workflow step’s progress entry. For example, if previously there was an assignment for “Submit passport copy” with status AWAITING_UPLOAD or SUBMITTED, now we would look at the worker_step_progress for the “Passport Copy” step; its status might go from PENDING to COMPLETED, and we’d track the file in a document submissions table.
Update Front-end API Usage: The front-end should stop calling any deprecated assignment endpoints. Instead, we will introduce new API calls:
A GET endpoint to fetch a worker’s workflow details (for WorkerProfile). This could be /api/workers/:workerId/workflows or included in the worker detail response. It should return the active workflow progress (if any) for that worker, including the list of steps with their statuses. We might include related data like step names, descriptions, and any document requirements or checklist items for each step (possibly pre-joined or via separate endpoints).
Endpoints to update step status or to mark tasks complete. For example, marking a step as completed or skipping it could be a PATCH on /api/workflows/step-progress/:id to update the status field (which uses a simpler enum like PENDING/IN_PROGRESS/COMPLETED). This would replace or augment the old PATCH assignment status route. We should implement such endpoints on the backend and adjust the front-end calls accordingly.
Document upload endpoints: Currently, file uploads for assignments use an endpoint /api/documents/upload-url that expects an assignmentId. We need to change this to use a workerStepProgressId or a documentRequirementId. For simplicity, we can allow the front-end to request an upload URL for a specific step progress. The backend can then generate a signed URL and eventually associate the uploaded file with that step (e.g., creating a document_submissions record linking the file to the worker_step_progress). We will refactor the front-end upload logic to pass the new identifier instead of assignmentId.
Data Migration / Backward Compatibility: If any existing data (assignments) is present, we should migrate it. This could mean writing a script or a one-time migration to create workflow progress and step progress records from the old assignments. Given that this is a development environment (Replit app), we might instead opt to drop legacy data and start fresh with the new system if possible. But if not, ensure that any ongoing assignments are properly mapped to the new schema so users don’t lose track of tasks.
Remove Legacy Code Paths: Clean up any components or pages that were specific to the old workflow system. For example, if WorkflowAssignmentsPage was a temporary UI to list all assignments, it might be obsolete once each worker profile shows their workflow. We could repurpose that page into a more useful overview of all workflows or remove it to avoid confusion. Also, eliminate any use of the old assignmentStatusEnum in the front-end; the statuses like AWAITING_UPLOAD or SUBMITTED_TO_INSTITUTION should be reflected either as step statuses or as fields on a submission (e.g., a submission could have a field indicating method of submission).
Align Workflow Rule Engine: The code snippet shows a workflow rules processor (triggering certain actions on events). If this is integrated with “assignments,” ensure it’s updated to work with the new data structures. For instance, if a rule triggers on “document uploaded” for a step, it should find the relevant worker_step_progress or document_submission rather than an assignment. This might be more on the backend side, but it’s part of making the system consistent.
Verify with New Workflow Data: After refactoring, test with actual workflow templates and a worker assigned to one. Create a workflow template in the system (if not already present) that has a couple of steps, and then assign a worker to it (we might need to create an interface or use the DB directly for this if the UI for assignment is not done yet). Then ensure that:
The worker’s profile loads the workflow progress without errors.
We can update a step’s status (simulate a user marking something done or an admin marking verified) using the new endpoints and see it reflected.
Document upload flow works with the new identifiers: the file gets uploaded to S3 and a record is created linking it to the appropriate step (the UI should show it as uploaded/received).
The statuses roll up correctly (e.g., when all steps are completed, the overall workflow could mark as completed).
By fully adopting the new template-based workflow system (with worker_workflow_progress and worker_step_progress replacing assignments), we ensure future scalability (multiple workflows, complex steps) and fix the current issue of missing workflow displays under workers.
