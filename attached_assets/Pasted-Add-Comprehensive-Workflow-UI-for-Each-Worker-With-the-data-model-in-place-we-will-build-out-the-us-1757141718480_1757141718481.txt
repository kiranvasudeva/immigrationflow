Add Comprehensive Workflow UI for Each Worker
With the data model in place, we will build out the user interface on the Worker’s profile to display and manage workflow progress. This will address the currently missing workflow display under each worker:
Workflow Section in Worker Profile: In the WorkerProfile page component, introduce a new section (below the worker’s personal details) titled something like “Current Workflow” or “Immigration Process”. This section will either show the active workflow steps or a message if no workflow is assigned.
If the worker has no workflow assigned: display a prompt for admins/owners to assign one. For example, a dropdown or modal that lists available workflow templates (e.g., “AJOFM + Work Permit”, “Visa D/AM”, etc.) fetched from the workflow_templates table. The user can select a template and click “Start Workflow” which will call an endpoint to create a worker_workflow_progress for that worker. After assignment, the UI should refresh to show the newly started workflow.
If the worker has an active workflow (which should be the common case after assignment): display the list of steps in order. This can be a simple vertical list or a more visual stepper/Kanban style. Given the mention of a kanban-style workflow in the design, we might use cards or a stepper component from Shadcn UI if available.
Display Step Details: For each step in the workflow (we’ll have the step name, description, and type from the workflow_steps template):
Show the step’s name (e.g., “Labor Market Test at AJOFM”) and current status (Pending, In Progress, Completed, etc. – using the worker_step_progress.status field).
If there is a due date or the order is important, include that (the steps do have an order and potentially due rules).
Under each step, list the requirements/documents needed for that step (from workflow_step_document_requirements). For instance, Step “AJOFM” might require a “Job Vacancy Announcement PDF” document. For each required document:
If the document is not yet submitted (no document_submissions record), show an Upload button or file input. The user (worker or owner) can click to upload the file. Use the file upload mechanism: call the /api/documents/upload-url (refactored to our new ID) to get a signed URL, then upload the file directly to storage. Upon success, call another endpoint or use the response to create a document_submission entry. Finally, update the UI: mark that document as “Submitted by User” and perhaps show a link or filename.
If the document has been uploaded and is pending review, show it as such (maybe an icon or badge “Submitted, awaiting admin”). Provide a link for admins to view/download the file (since PDF.js is integrated, perhaps clicking it could open a preview).
Also list any checklist items or approvals for the step (from checklist_items associated with the step). For example, after a document is submitted, an admin might need to verify it. These checklist tasks might be of type 'VERIFICATION' or 'APPROVAL'. In the UI, for each such checklist item:
Display the item title (e.g., “Verify job posting authenticity”) and who is responsible (assignedRole, likely ADMIN in these cases).
If the logged-in user is an ADMIN (or matching the assigned role), provide a toggle or checkbox to mark it completed. When toggled, call an endpoint (e.g., PATCH /api/checklist-completions/:id or a general step-progress update) to mark that item done. This could also update the worker_step_progress status if completing the item means the step is finished.
Indicate completion status with a checkmark or color change. Possibly use Shadcn UI’s Checkbox or Switch component for a nice UI.
Step Actions and Transitions: Include buttons or controls for actions like:
Mark Step as Completed: In some cases, a step might be manually markable as completed by an admin (for instance, if a step is something like “Submit application to IGI”, once done externally, admin can mark it completed). We could have a “Complete Step” button for such steps if all required items are done. This would set the step status to COMPLETED.
Mark as In Progress: Maybe when a user starts uploading or working on a step, we mark it in progress. This can be automated: e.g., when a file upload begins, set status to IN_PROGRESS.
Advance to Next Step: If the workflow is strictly sequential, after one step is completed, the next step’s status might automatically become active (IN_PROGRESS or at least no longer blocked). We should ensure the UI reflects this by perhaps enabling the next step’s section once the previous is done. This logic might already be handled in backend (the currentStepId in worker_workflow_progress could denote which step is currently active). The UI should highlight the current step and maybe gray out future steps until reached.
Handle Role Differences: Only show relevant controls to the appropriate users:
A Worker (or their Owner client) should be able to see their progress and upload documents, but not mark verifications or override statuses. So, if a worker is logged in viewing their own profile, they might see the steps and which are done/pending, and have an upload button for documents, but no admin toggles.
An Admin viewing a worker’s workflow should see everything plus the verification toggles and the ability to mark steps complete or even reject something (maybe mark a step or document as rejected with a reason, if a document is not acceptable).
The UI should use the user’s role (available via useAuth()) to conditionally render these controls.
Polish the UI: Make sure the workflow section is visually clear. Use badges or colors to show status (e.g., Pending = gray, In Progress = blue, Completed = green, Rejected = red). Possibly incorporate small icons (the Lucide icons like CheckCircle, AlertTriangle, etc., are already imported in some pages) to denote status. Keep the layout consistent with the rest of the app (likely using cards or list groups from Shadcn).
Testing Workflow UI: After building, test this thoroughly:
Create a scenario: assign a workflow to a worker that has at least one document requirement and one admin checklist. Then log in as a worker (or use the RoleSwitcher if in development mode) to upload a document. Verify the UI updates and the admin can see it.
Log in as admin, check that you can mark the uploaded document as received/verified, and the status changes appropriately (perhaps the step becomes completed if that was the only requirement).
Try edge cases: uploading wrong file type (the backend might enforce acceptedFileTypes), or an admin rejecting a submission (we might need to implement a reject flow – e.g., admin sets step status to REJECTED and the UI should handle that by maybe prompting re-upload).
Ensure that navigation away and back to the page reflects the latest data (i.e., our use of React Query should fetch current statuses on mount).
This comprehensive workflow UI will close the functionality gap where previously the worker’s workflow was missing or mocked. It provides transparency to clients/workers on their case progress and gives admins the controls needed to manage each step.
