Replace Mock Data with Real Database Integration
One of the highest priorities is eliminating any mock or hardcoded data so the app runs entirely on real database-backed data. We will:
Identify All Mock Data Uses: Search the code for any temporary data arrays, dummy objects, or placeholder fetch functions. For example, the industries list for client CAEN codes might be an array in the front-end – this should be replaced. If a static list of industries is needed and not yet in the DB, we can move it to a config file or at least define it in one place rather than scattered in the UI. Another example is the Reminder Rules fetch: currently the Reminders page calls an API but uses a dummy query function returning [] (empty list) because the endpoint isn’t implemented. For such cases, if implementing the backend is out of scope, we may hide or disable that UI until it’s ready, or better, implement the missing API endpoint so the feature becomes functional.
Wire Up Real API Calls: Every page (Dashboard, Clients, Workers, etc.) should retrieve data via the actual API endpoints (which in turn use the DB). If any page is currently using a stubbed response, change it to call the appropriate endpoint. For instance:
The Clients page should use a real GET /api/clients endpoint to list clients from the database. Ensure this endpoint returns all needed fields (including perhaps a unified company name field).
The Workers page should call GET /api/workers (or similar) to fetch the list of workers.
The Dashboard’s summary metrics should be computed either on the server side or fetched via a dedicated endpoint. If no such endpoint exists (e.g., for performance stats), consider creating one or performing the aggregation in the front-end using data from other endpoints (but be mindful of efficiency).
Remove Hardcoded Dropdown Data: Replace any hardcoded select options (like industry sectors, country lists, etc.) with dynamic data. This could mean querying the database for these values or moving the list to a constants file. For example, if there is a static list of countries or industries in the UI, it could be moved to a JSON or fetched from an API (/api/constants/industries if available, or simply use a centralized constants module).
Use Drizzle/Prisma via API, Not Directly in UI: Ensure the front-end does not directly import any data models or touch the database; it should always go through the back-end API. The back-end already uses Drizzle ORM to interact with PostgreSQL, so all actual data should come from back-end routes. We might need to implement new routes in Express if some data was only mocked and no route existed. For instance, if “industries” are to come from DB, perhaps we add a route /api/industries that returns a list from a table or a static JSON.
Test with Real Data: After hooking up real data sources, populate the database (via the app’s UI or direct DB inserts) with sample clients, workers, and workflow templates to verify that the UI now renders actual content. This will immediately reveal if any component was reliant on the shape of mock data that differs from real data. We should fix any mismatches (for example, if the mock had a field that the real API doesn’t send). In short, every piece of displayed information should be coming from a live database query. No more dummy placeholders – if something is not implemented yet and cannot be fetched, it’s better to remove that UI element or clearly mark it as not available, rather than leave a hardcoded stub.
By the end of this step, the app’s pages will be truly functional from the data perspective: clients, workers, and other lists populated from the actual DB, with no fake data. This lays the groundwork for consistent data handling in subsequent steps.
