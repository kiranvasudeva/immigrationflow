Preserve Existing Functionality and Prevent Regressions
During the rebuild, it’s critical that we don’t break anything that currently works. To achieve this, we will adopt a careful, incremental approach with continuous verification:
Iterative Development: Tackle one aspect at a time (as outlined in steps 3–6) and test it before moving on. For example, after replacing mock data with real API calls (Step 3), run the app and ensure the pages still render and show data correctly. Then after unifying data models (Step 4), verify that you didn’t accidentally break a component by renaming a prop incorrectly. This step-by-step integration helps isolate issues and makes debugging easier.
Automated Verification: Utilize the provided verification tools frequently. After significant changes, run node scripts/verify-frontend.js to catch any TypeScript errors or obvious failures. This script likely runs linting, type-checking, and maybe some basic interaction tests. Fix any errors it reports immediately (e.g., missing fields, wrong types due to model changes).
Console and Network Monitoring: Keep an eye on the browser console while testing the app manually. The goal is to have no red errors in the console. Common runtime errors might include trying to read undefined properties (often due to mismatched data keys) – if such errors appear, address them by adjusting the code (adding optional chaining as needed to handle nulls safely, or ensuring data is properly fetched before rendering). Also, watch the network tab in dev tools: ensure all XHR/Fetch requests return 200 status, not 404 or 500. If any request is failing after our changes, debug that (it could indicate a misnamed endpoint or a server error from unexpected input).
Manual Regression Testing: Go through a checklist of core features after each major refactor:
Authentication Flow: Log in (if possible in the dev environment) and ensure the app still recognizes the user role and shows the appropriate dashboard. We must not break the Replit Auth integration.
Basic CRUD: Create a new client and new worker via the UI forms to confirm those still work (forms should validate and submit properly). Then try editing an existing client/worker to verify our fixes. Delete functionality (if exists) should be tested too.
UI Interactions: Click all buttons and links you can find: sidebar toggles, navigation links, “edit” buttons, etc., to ensure they all do something meaningful and don’t throw errors. Modals and dropdowns should still open properly. For example, opening the “New Client” modal should still work and pre-filling forms should still clear out after submission (no stale state issues).
Role-based checks: Use the RoleSwitcher (if available in dev mode) to simulate different roles (ADMIN, OWNER, WORKER) and verify the UI adjusts as expected (some pages might be off-limits to certain roles, which should redirect or show an unauthorized message – ensure those still function).
Never Disable Existing Tests: If the project has unit or integration tests (perhaps via Vitest or Playwright as suggested by the architecture docs), run them and make sure they pass. Do not simply remove or change tests unless the requirements changed; instead, update the code to satisfy the tests and the new behavior. This ensures we catch regressions.
Maintain Working Features: If a component or feature is already working fine (e.g., maybe the “Audit Logs” page or the “Analytics” page, if those were fully implemented), try to avoid making changes that could affect it unless necessary. For instance, our refactor focus is on clients, workers, workflows – we should still double-check that pages like Audit Logs, Reminders, Templates, etc., load without errors after our changes (since data model changes could have ripple effects).
Frequent Commits/Backups: As an AI writing prompts for code changes, ensure to suggest that the user save the state frequently. If using Replit’s version control or Git, commit after each step. That way, if something goes wrong in Step 6, one can rollback to the state after Step 5 which was known good. This is a safety net against large regressions.
Consult the Checklist: The documentation provides a Frontend Testing Checklist – use it as a guide each time. Forms (check), CRUD (check), API responses (check), UI state (check), network (check), etc. By methodically verifying each category, we can be confident nothing important is broken. Remember, “never break existing working functionality” is a key directive, so if anything fails during these regression tests, pause and fix it before proceeding.
By keeping regression prevention at the forefront, we ensure that the end result is not only feature-complete but also stable and reliable, with all previously functional components still working correctly.
