Enforce Consistent Data Models Across Pages
To resolve mismatches like 'companyName' vs 'legalName' and ensure all parts of the app use the same data shape, we will standardize the data model usage:
Unify Client Name Field: Decide on a single source of truth for the client’s name. The database uses legalName (the official company name), which is appropriate. The API can transform this if needed (for instance, some endpoints might return a field called company or companyName). We should eliminate confusion by using one term consistently. The simplest approach is to use legalName everywhere on the front-end when referring to a client’s name. That means updating any component or logic that currently expects companyName. For example, in the Dashboard’s summary, change assignment.clientProfile?.companyName to .legalName (or ensure the assignment data includes a clientProfile.legalName). Similarly, on the Clients page list, ensure the column for name uses legalName. If the backend’s client list response uses a different property (e.g., company as in the clientResponseSchema), either adjust the backend to also use legalName or map that field in the front-end. The goal is that all references to a client’s name are consistent, preventing undefined values and confusion.
Align Worker Data Representations: Check that the Workers page and related components use the same field names as the API provides. For instance, if the worker list API returns fullName and email for each worker, the front-end should use those rather than reconstructing names or using a different field. Ensure that worker profile details (DOB, nationality, etc.) match between what the form expects and what the DB sends. If there’s any discrepancy (like the DB returns passportExpiry as a date but the front-end expects a string), handle the conversion either in the API or when setting initial form values. Standardizing on the schema defined by the zod schemas in the shared code (like workerResponseSchema) will help avoid state mismatches.
Fix Edit Form Field Mismatches: One known issue is that editing a client or worker currently doesn’t work due to state mismatches. This likely means the edit form’s controlled components have different naming or structure than the data loaded. For example, maybe the edit form uses a local state like editClientForm.companyName but the data from the server is legalName, so nothing populates. We will fix this by using React Hook Form for editing (consistent with architecture) and ensuring the defaultValues for the form correspond exactly to the field names in the form. If the form fields are named legalName, registrationNumber, ..., then the object we load from the server should be mapped to those keys. We saw that on creation, they have newClientForm.legalName, etc., so presumably the edit form should also use legalName. We will adjust the code so that when loading a client’s data for editing, we do: reset(formDataFromServer) where formDataFromServer has properties legalName, registrationNumber, ... matching the form. This will eliminate undefined values and allow the user to see and edit the current info. Similarly, for worker editing, make sure fields like date of birth are handled consistently (converting Date to string for input, etc., as seen in the Zod transform for dates in the schema).
Standardize Data Shaping in Components: If any component was transforming data in an inconsistent way (for example, constructing a display name differently on different pages), refactor them to use a common helper or rely on the API. For instance, if the full name of a worker is needed, perhaps the backend already provides fullName. Use that instead of concatenating firstName/lastName in multiple places. This reduces divergence. Another example: address formatting might differ between dashboard and profile page – we should standardize how addresses or other composite fields are displayed.
Ensure Dashboard Uses Unified Models: The Dashboard often combines clients, workers, and assignments data. After migrating workflows (in the next steps), the Dashboard should be updated to use the new workflow progress data for its stats. But even prior to that, audit what fields it uses. If it shows “Total Clients” or lists “Recent Workers”, ensure it’s using the same API that the Clients/Workers pages use. If it was using a separate data structure or mock, unify it so that it calls the client and worker services (or an aggregate service) rather than any duplicated logic. This will prevent the kind of inconsistency we saw with client names.
Testing for Consistency: Once changes are made, test by navigating through the app: the same client name should appear on Dashboard cards, in the Clients list, and in the Worker’s detail (where the client is referenced), with no missing data. Edit a client and a worker to verify the forms load the existing values and saving updates them. These tests will confirm that our data model usage is now uniform across the application.
By enforcing a consistent data shape, we not only fix current bugs (like missing names or non-functional edits) but also make the code easier to maintain, since every part of the app “speaks” the same data language.
